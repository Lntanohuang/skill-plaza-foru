# 049 · 精确岗位名候选查询与括号标题分布试验

- 状态：已实现（合并岗位统计工具接入完成；精确标题索引仍未落地）。
- 动机：验证将岗位名 `LIKE` 改为 Agent 生成的有限全称候选 `IN (...)` 是否明显提速，并确认岗位名中的括号变体是否值得纳入候选扩展。
- 约定细节：使用 `scripts/mysql-query.mjs` 只读执行，口径为广州市、Java、后端/服务端/开发、实习。`title-top` 真实返回 7 个岗位名，其中 4 个含半角或全角括号：`java开发实习生(提供转正)`、`Java开发工程师（实习生）`、`Java开发工程师-25届秋招 (MJ000381)`、`Java后台开发工程师（实习岗可转全职）`。库内在招未删除岗位共 9,617,002 条，其中含括号岗位记录 334,502 条（约 3.48%）；不同岗位名 1,346,533 个，其中含括号岗位名 274,259 个（约 20.38%）。目标实习切片 10 条记录中 4 条含括号（40%），7 个不同岗位名中 4 个含括号（约 57.14%）。
- 实测：当前 `c_company_position` 没有普通 `name` B-tree 索引，只有 `ft_position_name` FULLTEXT；对上述 7 个真实标题执行 `p.name IN (...)` 的 EXPLAIN 仍选择 `publish_state_index`，估计扫描 4,789,551 行。相同口径两轮交错对比：精确 `IN` 为 34.775s / 30.255s，原 `LIKE` 为 30.159s / 30.584s；结果均为 10，未观察到明显提速，说明在没有 `name` 索引且地址 JOIN 未优化时，精确谓词不能改变主要扫描瓶颈。
- 成本与取舍：括号标题在总体记录中不多，但在小样本实习切片中占比高，不能简单删除括号内容；精确候选应保留括号变体或采用仅规范空白/括号形式的归一化。Agent 多次查询会放大数据库压力，若继续试验应合并为单次 `IN`；但在建立 `name` 索引前不应宣称有性能收益。当前数据库账号仅 SELECT，未执行 DDL。
- 后续扩展路线：先由库主执行 `INDEX(name)` 或与地址关联字段组合的候选索引，再对同一候选集合做 `EXPLAIN ANALYZE`/实际耗时对比；同时用真实 title-top 结果构造候选，不让 Agent 盲猜任意标题。若采用候选扩展，保留原 `LIKE` 作为低样本兜底，括号内容不直接丢弃。
